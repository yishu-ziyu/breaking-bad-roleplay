# 黑客松产品开发生命周期：完整行动清单

> 来源：基于 2026 年黑客松实践、API-first 开发方法论、产品管理框架的综合调研。
> 适用场景：24-72 小时黑客松、AI 辅助开发（Claude Code / TRAE / 多 Agent 并行）

---

## 一、Discovery & Scoping：写代码之前必须回答的 6 个问题

### 核心原则
> 42% 的初创公司失败是因为做了没人想要的东西。黑客松不是"能不能做出来"的考试，是"值不值得做"的考试。

### 必答问题清单（在写任何代码之前）

**Q1：用户是谁？用一句话描述**
- 错误写法："年轻人"
- 正确写法："22-28 岁一线城市刚养猫的白领，每周丢一次猫砂，痛点是下班回家猫砂盆满了"
- 检验标准：你的描述能不能帮你决定"这个功能做还是不做"

**Q2：具体痛点是什么？当前怎么解决的？**
- 要求：写出用户当前的真实行为（不是理想行为）
- 格式："用户现在用 XXX（竞品/手工/Excel），每次遇到 YYY 问题"
- 关键测试：如果这个痛点不存在，用户会主动寻找解决方案吗？

**Q3：为什么是现在？外部趋势是什么？**
- 检查：最近 6 个月有什么变化让这个方案更可行？
- AI 黑客松场景：某个 API 成熟了？某类数据开放了？某个模型能力突破？

**Q4：什么是"不做就出局"的核心功能？**
- 使用 **MoSCoW 法则**分类：
  - **Must**（必须有）：没有它产品完全不能工作
  - **Should**（应该有）：显著提升体验但不是核心
  - **Could**（可以有）：锦上添花
  - **Won't**（这次不做）：明确放弃
- 黑客松铁律：Must 不超过 3 个，Should 不超过 2 个

**Q5：什么是成功的 demo？**
- 格式："评委在 3 分钟内看到 XXX 流程完整跑通"
- 具体描述：用户打开页面 → 输入什么 → 看到什么结果 → 解决了什么问题
- 反面教材：demo 依赖网络请求、依赖第三方 API 密钥、依赖特定硬件

**Q6：如果只有 20% 时间，保底功能是什么？**
- 设计一个"保底方案"：最简版本的核心功能
- 即使所有花哨功能都做不完，保底方案必须能演示
- ArcBlock 获胜者策略："先实现一个更简单的版本保底，再花时间完善"

### MVP 范围定义模板

```
产品名：_________
一句话描述：_________
目标用户：_________
核心痛点：_________

Must（必须有）:
1. [ ] _______
2. [ ] _______
3. [ ] _______

Should（应该有）:
1. [ ] _______
2. [ ] _______

Could（可以有）:
1. [ ] _______

- _______
- _______

Demo 脚本:
1. 用户打开 _______
2. 输入 _______
3. 看到 _______
4. 效果是 _______
```

## 二、Architecture Alignment：前后端不同步的根治方案

### 核心原则
> "后端准备好了"是一个诅咒。API 契约（Contract）是唯一的真相源。

### API-First 开发协议（适用于 Agent 并行开发）

**第 0 步：在写任何代码之前，写出 API 契约**

用 OpenAPI YAML 或 JSON 定义：
- 每个端点：路径、方法、请求参数、响应结构
- 每个字段：类型、是否必填、示例值
- 错误状态码：什么情况下返回 400/401/403/404/500
- 认证方式：Header / Token / None

**第 1 步：契约评审（前后端 Agent 都要读）**
- 前端 Agent 确认：响应结构能满足 UI 需求吗？字段够用吗？
- 后端 Agent 确认：这个结构能从前端数据模型推导出来吗？
- 产品 Agent 确认：这个端点实现了什么用户动作？

**第 2 步：契约即代码**
- 后端：用契约生成服务端骨架（Stub），填业务逻辑
- 前端：用契约生成 TypeScript 类型 + Mock Server
- 工具：OpenAPI Generator / Prism / MSW（Mock Service Worker）

**第 3 步：并行开发，禁止口头协议**
- 契约文件放在共享位置（monorepo 的 `contracts/` 目录或独立 repo）
- 任何修改必须同时更新契约 + 通知另一方
- 口头说的"加个字段"不算数，必须改契约才算

**第 4 步：集成前检查**
- 运行契约测试：验证后端实际返回是否符合契约定义
- 工具：Dredd / Spectral / 自写断言
- 不通过的契约 = 不能合并

### 前后端 Contract 检查清单

```
[ ] OpenAPI / GraphQL Schema 已编写
[ ] 前后端 Agent 都读过契约并确认
[ ] 字段名/类型/必填性无歧义
[ ] 错误响应格式已定义
[ ] 认证方式已明确
[ ] 前端已生成 TypeScript 类型
[ ] 前端已配置 Mock Server
[ ] 后端有契约测试 CI
[ ] 任何修改走 PR → 评审 → 更新契约
```

### 常见陷阱

| 陷阱 | 表现 | 解法 |
|------|------|------|
| 数据库思维 API | 返回 47 个字段，前端只需要 3 个 | 契约由前端驱动设计 |
| "后端快好了" | 前端干等 3 周 | 契约先行，Mock 先行 |
| 静默变更 | 后端改了字段名没通知，生产环境炸了 | 契约版本化 + CI 检查 |
| 瀑布集成 | 最后一天才接在一起，全是 Bug | 每日小集成，非最后大爆炸 |

## 三、Feature Inventory：功能错配的系统性检测方法

### 核心原则
> 你不知道自己缺了什么，直到 demo 那天发现按钮点了没反应。

### 三步功能审计法

**第 1 步：列出后端实际提供的（真集）**
- 扫描路由/控制器文件，提取所有端点
- 记录：方法、路径、请求体结构、响应结构
- 排除：未完成的 / 注释掉的 / 只有 Stub 没有逻辑的

**第 2 步：列出前端期望的（需集）**
- 扫描所有 `fetch` / `axios` / API 调用
- 扫描所有表单提交目标
- 记录：调用位置、期望的 URL、请求体、期望的响应字段

**第 3 步：对比找缺口**
- 前端调用了但后端没有 → 缺失端点
- 后端有但前端没调用 → 可能是遗漏或未完成功能
- 两端都有但字段不对 → 类型不匹配

### 自动化检测脚本思路

```python
# 伪代码框架
def audit_features(backend_routes, frontend_calls):
    backend_urls = {r.path + r.method for r in backend_routes}
    frontend_urls = {c.url + c.method for c in frontend_calls}
    
    missing_in_backend = frontend_urls - backend_urls
    unused_in_frontend = backend_urls - frontend_urls
    
    # 字段级对比
    for call in frontend_calls:
        endpoint = match_endpoint(call, backend_routes)
        if endpoint:
            check_fields(call.response_fields, endpoint.response_schema)
    
    return {
        "missing_endpoints": missing_in_backend,
        "unused_endpoints": unused_in_frontend,
        "field_mismatches": [...]
    }
```

### AI CT 扫描法（适合复杂项目）

给 AI Agent 的指令模板：
```
1. 先读取项目结构，理解整体架构
2. 生成"已落地功能清单"——每个端点/组件/页面实际做了什么
3. 生成"规划功能清单"——PRD/README/设计文档中计划了什么
4. 逐项对比两份清单，标记：
   - 计划中有但代码中缺失的
   - 代码中有但计划中没有的
   - 两边都有但行为不一致的
5. 输出"问题整改清单"按优先级排序
```

### 检查清单

```
[ ] 每个前端页面都能调到后端数据
[ ] 每个表单提交都有对应后端端点
[ ] 每个后端端点都被至少一个前端页面使用
[ ] 错误状态（加载中/空数据/失败）都有 UI 处理
[ ] 所有 API 调用有 fallback 或错误提示
[ ] 演示脚本走一遍，没有 404 / 500
[ ] 没有"半成品"按钮（点了没反应的）
```

## 四、Dead Code Detection：僵尸 UI 的识别与清理

### 什么是僵尸 UI

- 有前端组件/页面，但对应后端功能从未实现
- 有按钮/链接，但点击后路由不存在或返回 404
- 有表单，但提交后没有后端处理
- 有页面引用了不存在的 API 端点

### 手动检测法（黑客松适用）

**路由扫描**
```
# 列出前端所有路由/页面
# 逐个打开，检查：
- 页面能否加载？
- 页面有没有数据？
- 数据是从哪里来的？那个端点存在吗？
```

**按钮/交互扫描**
```
# 列出所有有交互的组件
# 逐个点击，检查：
- 点击后有没有效果？
- 控制台有没有报错？
- 是"真的功能"还是"占位符"？
```

**API 调用扫描**
```
# 前端代码中 grep 所有 fetch/axios/API 调用
# 对照后端路由列表
# 标记出：前端调了但后端没有的
```

### 检测工具

| 工具 | 用途 | 适用场景 |
|------|------|---------|
| ESLint `no-unused-vars` | 检测未使用的变量/导入 | 前端代码级 |
| `knip` | 检测未使用的文件/导出/依赖 | 全项目级 |
| 42Crunch API Scan | 对比 OpenAPI 契约与实际行为 | API 契约验证 |
| Prism (Stoplight) | Mock Server + 契约验证 | 开发阶段 |
| 自写审计脚本 | 前后端功能对比 | 快速审计 |

### 僵尸代码决策矩阵

| 类型 | 判断标准 | 行动 |
|------|---------|------|
| 纯占位组件 | 没有 API 调用，硬编码假数据 | **删除** |
| 半成品功能 | 有 UI 但后端没接上 | **标为 WON'T** 或 **快速接上** |
| 遗留功能 | 之前能用但现在断了 | 检查是否故意下线，决定修复/删除 |
| 调试代码 | `console.log`、临时 API | **清理** |

### 黑客松专属清理策略

> 时间有限，不要花 30% 时间做完美清理。按优先级清理：

1. **演示前必须清**：任何演示时会点到/看到的僵尸 UI
2. **快速清**：用 `git rm` 删掉整个未完成页面，比修起来快
3. **标红清**：来不及删的，在代码里加 `// TODO: 移除 - hackathon only` 标记

## 五、Hackathon-Specific Best Practices

### 时间盒策略

| 阶段 | 时间分配（以 36 小时为例） | 核心任务 |
|------|--------------------------|---------|
| 0-2h | 10% | 定义 MVP、写契约、团队分工 |
| 2-14h | 35% | 后端核心功能 + 前端骨架 |
| 14-24h | 30% | 两端集成 + 核心流程跑通 |
| 24-30h | 15% |  Polish + 边界情况 |
| 30-36h | 10% | Demo 准备 + 排练 |

### 时间陷阱清单（每个都是真实的坑）

| 陷阱 | 预估耗时 | 规避策略 |
|------|---------|---------|
| 认证/用户管理 | 4-6h | 用第三方登录（钱包/OAuth），不要自建 |
| 部署配置 | 2-4h | 提前选好平台，写好 Dockerfile 模板 |
| 边缘情况处理 | 2-4h | 只处理 happy path，其他记 TODO |
| 设计调优 | 3-5h | 用组件库，不像素级调优 |
| 范围蔓延"再加一个功能" | 无限 | **第 20 小时后禁止新功能** |
| 集成 Bug | 3-8h | 契约先行，每日小集成 |

### MVP 铁律

1. **一个核心功能做到极致，好过五个功能都半吊子**
2. **部署是第一道门槛**：没部署 = 评委直接跳过
3. **Web 端优先**：App/小程序部署成本高，Web 最快
4. **保底方案必须有**：复杂创意先做简化版保底
5. **第 20 小时红线**：之后只能修 bug 和 polish，不能加功能

### 常见失败模式

| 失败模式 | 表现 | 原因 | 规避 |
|---------|------|------|------|
| 演示崩溃 | 现场 API 不通/数据库挂了 | 依赖外部服务 | 录制备用视频 |
| 功能断裂 | 按钮点了没反应 | 前后端没接上 | 功能审计 |
| 过度工程 | 花 6h 做通用框架 | 过度设计倾向 | 问"这解决当前问题吗？" |
| 范围蔓延 | 想加的功能越来越多 | 没有明确的 Must 列表 | 写下来，贴墙上 |
| 团队协作混乱 | 两个人改了同一个文件 | 没有分工协议 | 契约 + 明确模块边界 |
| 演示差 | 代码很棒但讲不清楚 | 没排练 | 至少排练 3 遍 |

### Demo 准备清单

```
[ ] 录制备用视频（网络/服务挂了直接播放）
[ ] 演示脚本写下来（每步操作 + 预期结果）
[ ] 至少排练 3 遍（计时，不超过 3 分钟）
[ ] 准备回答评委可能的 5 个问题
[ ] README 写清楚：做了什么 + 怎么做的 + 亮点
[ ] 代码提交历史清晰（评委会看 git log）
[ ] 提前测试部署环境（不要 demo 当天才部署）
[ ] 准备离线版（如果现场网络差）
```

### 黑客松 judging 标准（综合多场比赛）

| 维度 | 权重 | 关键问题 |
|------|------|---------|
| **完成度** | 20-35% | 功能是否真的跑通了？还是 PPT 产品？ |
| **创意/创新** | 15-25% | 想法是否新颖？解决了什么真实问题？ |
| **商业价值** | 15-20% | 这个产品有人愿意用/付费吗？ |
| **技术难度** | 10-20% | 有没有技术突破？还是 CRUD 堆砌？ |
| **用户体验** | 10-20% | UI 是否清晰？操作是否流畅？ |
| **演示质量** | 10-15% | 能否在 3 分钟内讲清楚价值？ |

> 来自 Polkadot 2024 / TiDB 2024 / ETHShanghai 2025 / 南京大学 Hackathon 的实际评分标准。

## 六、Product Thinking for Engineers：从"代码能跑"到"产品有用"

### 三种思维模式对比

| 维度 | 工程思维 | 产品思维 |
|------|---------|---------|
| 关注点 | 代码质量、性能、架构 | 用户价值、商业目标 |
| 决策依据 | 技术可行性、最佳实践 | 用户需求、ROI |
| 成功标准 | 功能完成度、Bug 数量 | 用户满意度、业务指标 |
| 时间视角 | 项目交付时间 | 产品生命周期 |
| 自我追问 | "这个功能怎么实现？" | "为什么需要这个功能？" |

### 产品思维的核心问题清单

在做任何功能之前，问自己：

**为什么层：**
- 这个功能解决什么具体问题？
- 谁有这个问题？他们现在怎么解决的？
- 如果没有这个功能，会发生什么？

**价值层：**
- 用户愿意为这个功能付出什么代价？（时间/金钱/学习成本）
- 这是 Must（没有就不行）还是 Could（有了更好）？
- 和竞品比，我们的差异化是什么？

**场景层：**
- 用户在什么情境下使用这个功能？
- 一次成功的使用流程是什么样的？
- 最可能的失败路径是什么？

**取舍层：**
- 做这个功能的代价是什么？（时间/复杂度/其他功能的机会成本）
- 不做会有什么后果？
- 有没有更简单的方案达到同样目的？

### 需求优先级框架（黑客松精简版）

**KANO 模型快速判断：**

| 类型 | 特征 | 例子 | 黑客松策略 |
|------|------|------|-----------|
| 基本型 | 没有 → 用户极度不满 | 登录、数据持久化 | **必须做** |
| 期望型 | 越好越满意 | 搜索准确度、响应速度 | 尽量做 |
| 兴奋型 | 没想到但很爽 | AI 个性化推荐 | 有时间就做 |
| 无差异型 | 有无皆可 | 换肤、暗黑模式 | **不做** |
| 反向型 | 做了反而反感 | 强制注册才能看 | **绝对不做** |

**RICE 快速评分（适合功能间取舍）：**
```
RICE = (Reach × Impact × Confidence) / Effort

Reach:  影响多少用户？（黑客松场景 = 1 = 评委看到）
Impact: 对单个用户的影响程度 1-5
Confidence: 对这个判断的信心 0.5/0.8/1.0
Effort:  需要多少小时？

分数最高的先做。
```

### "这个功能有用吗？"决策红绿灯

```
绿灯（直接做）：
- 解决用户说的具体痛点
- 是 Must 级需求
- 能在 2 小时内完成

黄灯（先问再决定）：
- "技术上很酷"但用户价值不明确
- 需要 4+ 小时
- Could 级需求
→ 问：不做会影响 demo 效果吗？不会就后移

红灯（明确不做）：
- 为了展示技术能力而做
- "反正挺简单的，顺便加上"
- 没有对应具体用户需求
- 需要超过 8 小时
```

### 工程思维 vs 产品思维：一个真实对比

> 蒸包机案例（来自产品经理实战分析）

**老板（用户思维）：**
"做一个智能蒸包机，扫码选包子，自动出餐，省掉一个服务员。"

**工程师（工程思维）：**
"需要摄像头、图像识别、TensorFlow 模型、定制电路板、RK3399 芯片、防热防潮处理……技术上完全可行。"

**产品经理（产品思维）：**
"等等——用户拿到手的包子是机器蒸的，干净吗？出错了怎么办？用户会不会担心食品安全？投入产出比算过吗？"

> 三种思维都对，但只有产品思维在"技术能做"和"用户愿意用"之间搭了桥。

### 工程师产品思维养成清单

```
每日自检：
[ ] 我今天写的代码，解决了什么用户问题？
[ ] 如果删掉这个功能，用户会 notice 吗？
[ ] 我有没有在解决"真实需求"还是"自嗨"？

每次评审前：
[ ] 这个功能上线后，用户数据会变吗？
[ ] 成功/失败的判断标准是什么？
[ ] 有没有更简单的实现方式？

每个 Sprint 结束：
[ ] 我们做的东西，用户能用一句话说清楚吗？
[ ] 有没有功能做完了但从没被使用过？
[ ] 下一次迭代应该往哪个方向走？
```
