## 一、背景与目标

产品中文输出存在"译制腔"风险（英文直译骨架、抽象+具体硬拼意象、英文舞台指示残留、音译乱写等）。此前已做两件事：

1. **守则注入**：在 prompt 的 `zh` 分支注入"中文母语者表达守则"，治本。
2. **守卫兜底**：检测命中 → LLM 重写，作为守则漏网时的兜底（PRODUCT_SPEC 承诺）。

本次复盘回答的核心问题：**守则到底有没有用？守卫到底值不值得上线？** 这决定了后续投入方向。

## 二、交付物

| 交付物 | 路径 | 说明 |
|--------|------|------|
| 请求级守则开关 | `zh_guard`（前端→后端→director） | A/B 的对照组基础，默认行为不变 |

## 三、A/B 盲测方法与结果

### 方法

"一个玩一个看"双 Agent 盲测：派浏览器 agent 用真实操作进入中文 Story 模式，同一角色、同一开场，分别跑对照组（注入守则）与实验组（`?zh_guard=0` 跳过守则），按三维度打分（母语自然度 / 英文语法痕迹 / 译制腔危害，各 1-10）。

### 结果（分差 = 对照 − 实验）

| 角色 | 母语自然度 | 英文痕迹 | 译制腔危害 |
|------|:---:|:---:|:---:|
| Walter | +2 | −3 | −3 |
| Jesse | +1 | −1 | −1 |
| Skyler | +2 | −2 | −3 |
| **平均** | **+1.7** | **−2.0** | **−2.3** |

### 判读

守则对中文质量有**稳定正向影响**：更自然、英文直译痕迹更少、译制腔危害更小。实验组（跳过守则）不会崩坏，但明显更书面、更舞台化、更接近字幕腔。

## 四、关键决策：守卫优先级下调

**结论依据**：盲测显示守则本身已把中文拉到 8 分档，实验组漏网率不高（+1.7 分差，非灾难级）。

**决策**：下调改写守卫的投入优先级。理由：
- 守卫是"把 8 分拉到 8.5 分"的边际优化
- 守则注入是"把 6-7 分拉到 8 分"的主防线
- 两者成本不成比例：守卫每命中一次需额外一次 LLM 调用（贵、需网络），漏网率本就低，边际收益有限

**执行**：保留守卫代码（作为探针与兜底），不优先上线。若线上扩散检查显示漏网率上升，再激活。

## 五、踩坑记录

1. **端口被无关项目占用**：首次盲测用 5173 端口，实际被用户机器上的 yishu-archive-site-vercel 占用，加载的是错误站点。本项目 dev server 实际跑 5174。已写死进盲测脚本，避免重蹈覆辙。
2. **搜索 agent 误报**：初盘时将"已实现"的 Marie / McKee 价值翻转门禁 / 克隆 TTS 误判为"未执行"。CEO 需亲自核对代码现状，不能盲信 agent 盘点。

## 六、经验沉淀

- **便宜探针 → 决策**：先做低成本探针（检测器、zh_guard 开关）拿到信号，再决定是否投入重资源（守卫）。符合"先验证再投入"的原则。
- **Agent 盲测可复用**：双 Agent 盲测（一个玩一个看）+ 请求级开关，是验证对话质量改动的通用方法，已沉淀为脚本。
- **CEO 职责**：不读代码，但要能核对关键事实、判断优先级、识别 agent 误报。顶层形态决策与底层技术执行分离。

## 七、后续建议

- **线上扩散检查**：这是唯一未落地的三件套之一（人工 A/B 盲测已替代为 Agent 盲测）。埋点方案已定义（复用 `dubbing_guard_probe` 检测器 + 结构化日志，纯后端零成本），实施文档见 `docs/DIFFUSION_MONITORING.md`。下一步是落地埋点代码、跑 2-4 周拿基线。
- **Hank 实验组补齐**：Hank 首测只有对照组分数，如需完整四角色对比，可补跑实验组。
- **守卫激活触发条件**：埋点文档已给出建议阈值（dubbing 漏网率 > 5% 连续 7 天，或单日 > 20 条，且样本量 > 200 才成立），需产品确认后作为激活改写守卫的决策点。
